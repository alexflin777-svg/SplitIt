# SplitIT — актуальный backlog закрытой беты

**Обновлён:** 2026-08-06
**Цель текущего цикла:** получить проверяемый web-кандидат для закрытого теста людьми на реальных Android/iPhone. Это **не** Store-релиз.

## Как пользоваться этим файлом

- `bug_report.md` — журнал подтверждённых дефектов и доказательств.
- Этот файл — единственный упорядоченный backlog. Исторические пункты из `progress.md`, `handoff*.md`, старого PRD и roadmap не являются актуальными задачами.
- На одну задачу назначаются независимые Maker и Checker. Maker работает в отдельной ветке/worktree; Checker не принимает результат без запуска проверок.
- До изменений схемы — отдельная новая миграция. Нельзя переписывать применённые миграции.
- Нельзя отмечать задачу выполненной по старому отчёту: требуется свежий вывод команды, скриншот или ссылка на CI/деплой.

# P0 — блокеры доверенного beta-кандидата

## P0-1. Сделать тестовый рантайм воспроизводимым

**Проблема.** Тесты `.mjs` импортируют TypeScript напрямую (`test/currency.test.mjs`, `test/realistic-rls.test.mjs`), но текущий Node 20.17.0 выдаёт `ERR_UNKNOWN_FILE_EXTENSION`. При этом CI использует Node 24, а локальная машина — Node 20; гейт нельзя воспроизвести.

**Границы.** Не менять денежную логику или миграции ради раннера. Выбрать один поддерживаемый способ: закрепить Node ≥22.6/24 для всех сред либо добавить явный TypeScript runner/предсборку и зафиксировать его в зависимостях.

**Maker:** обновляет `package.json`, lockfile, CI и инструкции минимальным diff.
**Checker:** запускает гейт на чистой установке и в версии Node, указанной в проекте.

**Критерии приёмки:**
- `npm ci` и `npm run test:unit` проходят на документированной версии Node;
- `npm run test:rls` проходит полностью;
- `npm test` больше не зависит от неявно установленного loader;
- в CI и локальной инструкции указана одна совместимая версия Node;
- зафиксированы реальные количества тестов и команды, а не исторические числа.

**Проверки:** `npm ci`, `npm run lint`, `npx tsc --noEmit`, `npm run test:unit`, `npm run test:rls`, `npm test`.

## P0-2. Принять или откатить текущие незакоммиченные UI-изменения

**Проблема.** В рабочем дереве уже изменены `src/app/icon.svg`, `src/app/layout.tsx`, `src/app/page.tsx`, `package-lock.json` и добавлен `RELEASE_READINESS_REPORT.md`. Они не относятся к этому аудиту и не были проверены как единый кандидат.

**Границы.** Не смешивать эту работу с новыми замечаниями. Сначала владелец подтверждает состав изменения; Maker выделяет его в отдельный понятный commit либо владелец откатывает самостоятельно.

**Критерии приёмки:**
- `git diff --check` чист;
- UX-изменения имеют скриншоты 375×812 и desktop;
- нет регрессии favicon, safe-area и нижней навигации;
- Checker одобрил diff независимо.

## P0-3. Подтвердить production-конфигурацию Auth до приглашения тестировщиков

**Задача владельца в Supabase Dashboard.**
- Site URL: `https://split-it-ere9.vercel.app`;
- Redirect URL: `https://split-it-ere9.vercel.app/auth`;
- принять решение по Email Confirmation: отключить на ограниченную бету **или** настроить SMTP и проверить письмо;
- включить leaked-password protection, если это не ломает выбранный поток регистрации.

**Доказательство:** тест сброса пароля на отдельном beta-аккаунте возвращает на production `/auth`; регистрация и вход не блокируют тестировщика; решение и дата фиксируются в `bug_report.md`.

## P0-4. Контролируемо применить `20260802000000_group_participants.sql` к production

**Предусловия:** P0-1 зелёный; есть безопасный доступ к production Supabase; согласованы окно работ и rollback/restore-план.

**Maker-план:**
1. Проверить legacy-строки и подготовить точный preflight-вывод без данных пользователей в логах.
2. Создать backup/point-in-time restore согласно тарифу и возможностям проекта.
3. Применить только новую миграцию штатным инструментом Supabase.
4. Запустить безопасные `verify:prod`, `verify:realtime` и canary с проверенным cleanup.

**Критерии приёмки:** миграция отмечена применённой; нет orphan/NULL, нарушающих инварианты; проверка двумя аккаунтами подтверждает изоляцию и Realtime; cleanup не оставляет данных; результат приложен к `bug_report.md`.

# P1 — обязательно перед стартом human device beta

## P1-1. Зафиксировать UX первого мобильного сценария

**Сценарий:** открыть ссылку → регистрация/вход → создать событие → добавить расход → пригласить второго человека → увидеть обновлённый баланс → отметить расчёт.

**Дизайнер/UX:** проверить 375×812, 390×844, 412×915 и desktop 1280×720 на собранном `out/`.

**Критерии приёмки:**
- интерактивные элементы не перекрыты BottomNav или safe-area;
- кнопка «Создать событие» видна и нажимается без обязательной прокрутки пустого экрана;
- favicon не даёт 404/console error;
- состояния загрузки, offline/error и запрет доступа понятны и не выглядят как успех;
- контраст, фокус, label у форм и touch-targets проверены.

**Артефакты:** свежие скриншоты и Playwright-тест на каждую найденную регрессию.

## P1-2. Устранить несоответствие Node/Capacitor

**Проблема.** `npx capacitor --version` на машине с Node 20 завершается: Capacitor CLI v8 требует Node ≥22.

**Критерии приёмки:** локальная и CI инструкция фиксируют Node 22+ (предпочтительно совпадающий с CI); `npx cap sync` проходит после production-сборки; версия Node выводится в build-логе.

## P1-3. Сформировать воспроизводимый Android internal-test кандидат

**Границы:** не публиковать в Store и не коммитить ключи, APK/IPA или `.env`.

**Критерии приёмки:**
- production `out/` собран с проверенными публичными переменными;
- `npx cap sync android` успешен;
- APK имеет ясную маркировку `internal` и канал доставки с checksum, commit SHA и инструкцией установки;
- минимум два тестировщика на разных Android-устройствах прошли P1-5;
- release AAB и Play signing — отдельная Store-задача, не блокируют web beta.

## P1-4. Определить границу iOS beta

**Решение владельца:** либо web/PWA beta на iPhone Safari, либо TestFlight. Нельзя называть simulator/unsigned IPA готовым артефактом для физического iPhone.

**Для TestFlight обязательны:** Apple Developer account, signing identity, provisioning, archive от текущего commit, загрузка в TestFlight и установка на физический iPhone.

## P1-5. Выполнить human device test-pass

**Участники:** минимум 2 человека, 2 аккаунта, 1 общая группа; не использовать личные финансовые данные.

**Обязательные кейсы:**
1. Регистрация, выход, повторный вход и reset password.
2. Создание группы; приглашение через мессенджер; получатель вступает.
3. Расход в базовой и другой валюте; поровну и точные доли.
4. Изменение расхода на устройстве A появляется на B без ручного refresh.
5. Нечлен открывает прямой URL группы и получает отказ без утечки данных.
6. Расчёт и фиксация перевода; итог не содержит `NaN`, `Infinity` или отрицательных сумм там, где они запрещены.
7. Потеря сети/возврат сети: интерфейс честно сообщает состояние, данные не «успешны» до записи.
8. Фото реального чека: успешное распознавание и понятная ошибка при неуспехе.

**Критерий завершения:** результаты каждого кейса, модель ОС/браузера, build SHA и severity дефекта занесены в `bug_report.md`; S1/S2 закрыты или есть явно согласованный риск.

- Store-подготовка: release-keystore/AAB, TestFlight, privacy policy, скриншоты и метаданные — отдельный проект после beta-решения.
- Telegram WebApp: только после серверной проверки `initData`; клиентская проверка не принимается.

## Не входит в этот цикл

- Публикация в Google Play/App Store.
- Авто-вход Telegram без server-side верификации.
- Новые социальные функции, push-уведомления, платежи и крупный редизайн.
- Изменение исторических миграций или массовые рефакторинги без подтверждённого дефекта.

## Release gate: когда можно сказать «готово к новым тестам людьми»

Все пункты должны быть подтверждены в **свежем** commit/deploy:

- [ ] P0-1 и P0-2 закрыты независимым Checker.
- [ ] P0-3 подтверждён владельцем и отдельным beta-аккаунтом.
- [ ] P0-4 применён и live-verifier/canary зелёные, либо web beta явно переведена в локальный режим с честным ограничением.
- [ ] `npm run lint`, `npx tsc --noEmit`, `npm run test:unit`, `npm run test:rls`, `npm run build`, `npm test` зелёные на закреплённом рантайме.
- [ ] Есть mobile и desktop screenshots на собранном `out/`.
- [ ] Есть URL задеплоенного кандидата, commit SHA, дата деплоя и rollback-точка.
- [ ] Human-device test charter P1-5 подготовлен; реальные тесты ещё не считаются пройденными до фактических результатов.
