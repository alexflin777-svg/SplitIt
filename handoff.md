## 1. Цель проекта

**SplitIT (Сплит-Чек)** — приложение для разделения совместных расходов в группах:
поездки, аренда жилья, рестораны, вечеринки. Пользователь заводит событие,
добавляет участников и расходы, а приложение считает, кто кому сколько должен,
и сводит долги к минимальному числу переводов.

Ключевые свойства из `PRD.md`:

- Next.js 14 (App Router, TypeScript, Tailwind) + Supabase (PostgreSQL, Auth).
- Мультивалютность: RUB, USD, EUR, KZT, GEL, AED, TRY.
- Алгоритм упрощения долгов — минимальное число платежей в графе должников.
- OCR чеков через Tesseract.
- Offline-first: всё пишется в localStorage мгновенно, синхронизация с Supabase
  поверх этого.
- Дистрибуция: статический экспорт (`output: 'export'`) → Capacitor → APK и IPA,
  плюс веб-версия. По `LAUNCH_ROADMAP.md` первый этап — закрытая бета на 15–30
  тестировщиков через APK.

**Ограничение, определяющее почти все технические решения:** `output: 'export'`.
Серверного рантайма нет ни в APK, ни на статик-хостинге. Значит: нет API routes,
нет SSR, нет динамических маршрутов, которые не были собраны заранее.

## 4. Что пробовал — без результата

Раздел про тупики и потраченное впустую время. Он существует, чтобы следующая
роль не повторяла те же ходы.

### Ручное вождение браузера для проверки авторизации

Кликал по координатам, снятым со скриншота, и промахивался: скриншот отдаётся в
удвоенном разрешении, а координаты клика — в CSS-пикселях. Клик по кнопке «Войти»
на `y=1084` при высоте вьюпорта 812 уходил за экран, форма молча не отправлялась,
и это выглядело как дефект приложения. Плюс `read_page` отдавал закешированное
дерево, поэтому переключение вкладки «Вход» казалось несработавшим.

Потрачено около шести ходов. Итог: ручное вождение годится для разведки и
скриншотов, но проверять поведение форм надо Playwright — он и попал в цель с
первого раза, и остался в репозитории как регрессия.

### Массовая замена ссылок регулярками

Скрипт вставки импортов искал «последнюю строку, начинающуюся с `import`», и в
четырёх файлах воткнул новый импорт **внутрь** многострочного блока
`import { ... } from 'lucide-react'`. Сборка развалилась на `TS1003: Identifier
expected`. Чинилось вторым проходом, который ищет конец **выражения**, а не строки.

Отдельно: подстановка `router.push('/events/${newGroupId}')` по общему шаблону
увела на форму создания вместо созданного события. Поймал глазами при перечитывании
диффа, не тестом.

Вывод для CODEX: механическая замена по регуляркам в TSX требует ручной вычитки
диффа. Дешевле, чем править вручную, но не бесплатно.

### `AvatarResult` как размеченное объединение

Хотел `{ dataUrl: string; error: null } | { dataUrl: null; error: string }`, чтобы
TypeScript сам сужал тип после проверки `if (error)`. Не сужает: дискриминантом
может быть только литеральный тип, а `error: string` — не литерал. Заменил на
обычный интерфейс с явной проверкой `if (error || !dataUrl)`.

### Первая версия теста на контраст

Сравнивала цвет текста с фоном **карточки**. Внутри карточек есть собственные
подложки, поэтому аватар-эмодзи на синем градиенте засчитался как «белое на белом».
Плюс эмодзи вообще не подчиняются CSS `color` — они рисуются своими цветами.

Переписал: подъём до ближайшего предка с непрозрачной заливкой + пропуск строк без
букв и цифр. После этого пять экранов проходят, а на сломанном CSS падают все пять.

### Селекторы, написанные по памяти вместо чтения разметки

`getByPlaceholder(/Поездка|Название/i)` — в форме стоит «Например: Алтай 2026».
`paidBy` в тестовых данных — приложение читает `paidById`. Проверка названия
группы на экране баланса — он его вообще не показывает, там заголовок
«Баланс & Итоговый расчет».

Пять падений подряд, и ни одно не было дефектом приложения. Селекторы надо брать
из файла, а не из головы.

### Тест на плейсхолдеры «упал», и это было правильно

Проверка «в бандле нет строки `placeholder-splitit`» падала уже после починки
кода. Причина оказалась не в тесте: строка приходила из самого `.env.local`,
где лежали выдуманные значения. Настоящая починка — очистить `.env.local`, а не
ослабить проверку.

### MCP, которые не поднялись

- `supabase` — требует OAuth, в неинтерактивной сессии не авторизуется. Из-за
  этого инвариант И-5 (изоляция данных между пользователями) закрыт кодом, но
  не проверен вживую.
- `StitchMCP` — подключается, но отдаёт битую схему инструментов
  (`can't resolve reference #/$defs/ScreenInstance`). Это баг на стороне сервера
  Google, с нашей стороны не чинится.
- `alloydb-postgresql`, `antimetal`, `gitlab-orbit`, `google-developer-knowledge` —
  в `~/.gemini/config/mcp_config.json` их нет ни в одной из трёх копий файла.
  Похоже, это встроенные расширения Antigravity, а не MCP-серверы.

## 5. Что планирую дальше

Порядок — по убыванию блокирующей силы.

### 5.1. Подключить настоящий Supabase (блокирует три инварианта)

Пока `.env.local` пуст, три вещи нельзя ни включить, ни проверить: серверная

Заход целиком:
1. Завести проект Supabase, заполнить `.env.local` (ключи — за владельцем).
2. Применить `supabase/migrations/20260731000000_init_splitit_schema.sql`.
3. Написать RLS: пользователь видит только свои группы и группы, где он участник.
4. Проверить И-5 двумя реальными аккаунтами в двух профилях браузера — что данные
   не перетекают. Это единственная настоящая проверка скоупинга каналов.
5. Убрать локальную проверку пароля из основного пути, оставив её только как
   офлайн-фолбэк с явной пометкой.

### 5.2. Отдать S3-1 и S3-2 в ④ Gemini
