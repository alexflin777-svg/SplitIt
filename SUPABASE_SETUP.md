# Подключение Supabase

Код многопользовательского режима готов и проверен. Проект Supabase создаёт
владелец: это требует регистрации и входа через браузер.

Ниже ровно те шаги, после которых приложение станет многопользовательским.
Займут минут пятнадцать. **Шага 2 недостаточно пропустить наполовину:** ключи
без применённых миграций дают приложение, которое считает себя сетевым и падает
на каждом экране.

---

## Шаг 1. Создать проект

1. Откройте [supabase.com/dashboard](https://supabase.com/dashboard), войдите.
2. **New project**. Регион ближе к пользователям (для России — Frankfurt).
3. Запишите пароль базы: он понадобится для CLI и больше нигде не показывается.

## Шаг 2. Применить миграции

> **Этот шаг легко пропустить, и тогда приложение сломается тихо.** Ключи
> прописаны, режим переключается в сетевой, а таблиц нет — каждый экран
> получает `PGRST205: Could not find the table 'public.groups'`. Проверить,
> применены ли миграции, можно одной командой:
>
> ```bash
> curl -s -o /dev/null -w "%{http_code}\n" \
>   "$NEXT_PUBLIC_SUPABASE_URL/rest/v1/groups?select=id&limit=1" \
>   -H "apikey: $NEXT_PUBLIC_SUPABASE_ANON_KEY"
> ```
>
> `200` — схема на месте. `404` — миграции не применены.

Через панель управления, без установки CLI:

1. **SQL Editor** → **New query**.
2. Выполните по очереди, в этом порядке, каждый файл целиком:
   - `supabase/migrations/20260731000000_init_splitit_schema.sql`
   - `supabase/migrations/20260731000001_drop_permissive_rls.sql`
   - `supabase/migrations/20260731000002_multiuser_support.sql`

Через CLI, если предпочитаете:

```bash
npx supabase link --project-ref <ref-из-адреса-проекта>
npx supabase db push
```

**Проверка.** Выполните в SQL Editor:

```sql
SELECT tablename, policyname, cmd
FROM pg_policies
WHERE schemaname = 'public' AND qual = 'true' AND tablename <> 'exchange_rates';
```

Ожидаемый результат — пустая выборка. Если что-то нашлось, значит применилась
не та редакция миграции: политика с квалификатором `true` открывает таблицу
целиком и обнуляет все остальные правила.

## Шаг 3. Прописать ключи

**Settings → API**, скопируйте `Project URL` и `anon public`. В `.env.local`:

```
NEXT_PUBLIC_SUPABASE_URL=https://<ваш-проект>.supabase.co
NEXT_PUBLIC_SUPABASE_ANON_KEY=<anon public ключ>
NEXT_PUBLIC_APP_URL=https://<адрес-приложения>
```

`anon` ключ публичный по замыслу: он попадает в браузер и в APK, а доступ режет
RLS на стороне базы. **`service_role` ключ сюда вписывать нельзя** — он
обходит RLS и открывает всю базу любому, кто откроет исходники страницы.

`NEXT_PUBLIC_APP_URL` попадает в ссылки-приглашения, поэтому должен быть тем
адресом, по которому приложение реально открывается.

## Шаг 4. Настроить авторизацию

**Authentication → URL Configuration**:

- Site URL: адрес приложения.
- Redirect URLs: добавьте `<адрес>/auth` — по нему возвращается сброс пароля.

**Authentication → Providers → Email**: включён по умолчанию. Подтверждение
почты на время беты можно выключить (**Confirm email**), иначе тестировщики не
войдут, пока не настроен SMTP.

## Шаг 5. Пересобрать

```bash
npm run build
```

Переменные `NEXT_PUBLIC_*` вшиваются в сборку, поэтому смена ключей без
пересборки ничего не меняет — старые значения останутся в `out/`.

**Проверка, что ключи доехали:**

```bash
grep -rlE "https://[a-z0-9]{20}\.supabase\.co" out/_next/static/chunks/ >/dev/null \
  && echo "адрес проекта вшит в сборку"
```

**Важно про тесты.** Набор E2E написан под локальный режим и собирается
отдельным скриптом `build:test` с пустыми ключами — иначе прогон зависел бы от
того, что лежит в `.env.local` у конкретного разработчика. `npm test` делает это
сам. Отдельная проверка `e2e/build-mode.spec.ts` падает первой, если артефакт
собран не в том режиме.

## Что изменится в приложении

| | Без бэкенда | С бэкендом |
|---|---|---|
| Данные | localStorage одного устройства | общая база, доступ режет RLS |
| Вход | пароль сверяется локально | Supabase Auth |
| Участники | добавляются по имени | вступают по ссылке-приглашению |
| Приглашения | не работают, экран говорит об этом | одноразовый код со сроком жизни |
| Синхронизация | между вкладками | между устройствами через Postgres Changes |
| Сброс пароля | недоступен, экран говорит об этом | письмо от Supabase |

Режим определяется автоматически по наличию ключей — `isMultiUser()` в
`src/lib/store.ts`. Экраны про режим не знают: один и тот же код работает и
так, и так.

## Как проверить, что многопользовательский режим работает

Два браузерных профиля (или обычное окно и приватное), два разных аккаунта.

1. **A** регистрируется, создаёт событие, добавляет расход.
2. **B** регистрируется в своём окне. На главной у него пусто — событие A не
   видно. Это и есть работающий RLS.
3. **A** нажимает «Поделиться», копирует ссылку, отдаёт её **B**.
4. **B** открывает ссылку, видит экран приглашения, нажимает «Присоединиться».
5. Теперь **B** видит событие, участников и расходы. Баланс считается на обоих.
6. **A** добавляет ещё расход — у **B** он появляется без перезагрузки.
7. **B** выходит из группы. Событие снова пропадает из его списка.

Отдельно стоит попробовать сломать: пусть **B** откроет
`/events/detail?id=<id-события-A>` напрямую, ещё не вступив. Должен увидеть
«Событие недоступно», а не данные.

## Что уже проверено без облачного проекта

Политики RLS прогоняются на настоящем PostgreSQL — PGlite, тот же движок в
WebAssembly:

```bash
node --test test/rls.test.mjs
```

25 проверок: изоляция групп, расходов и профилей, невозможность вписать себя в
чужую группу, утечка кодов приглашений, подделка перевода от чужого имени,
ограничения на суммы, потеря доступа после выхода из группы.

Харнесс проверяет сам себя: если роль не переключилась на `authenticated` и
запросы идут под владельцем схемы (владелец обходит RLS), он падает с явной
ошибкой, а не зеленеет впустую.

Чего эта проверка **не** покрывает: PostgREST, GoTrue и Realtime. Их поведение
подтверждается только шагами из предыдущего раздела на живом проекте.
