## Что изменилось для пользователя (коротко)

1. **Правка расхода больше не портит доли.** Расход «по позициям» или с точными суммами открывается с настоящими долями; если ничего не менять, всё сохраняется как было, а если поменять сумму, доли пересчитываются пропорционально, и новые цифры видны до сохранения.
2. **Баланс и итог считаются по всем расходам**, а не по первым 50: в больших событиях суммы теперь сходятся.
3. **Можно отметить перевод с гостем** (у гостя нет аккаунта): любой участник события может записать «гость отдал мне» или «я отдал гостю».
4. **Гостя можно удалить из события** кнопкой «×»; если у гостя есть расходы, приложение прямо говорит: «У гостя есть расходы — сначала перенесите или удалите их».
5. **Готов пакет для закрытого теста Google Play:** тексты стора, черновик Data safety, письмо тестировщикам, версия 1.0.1; на сайте оператор данных — «Константа Лабс».

> Пункты 1 (в сетевом режиме), 3 и 4 заработают у пользователей **только после применения миграций** к боевой базе — см. «Миграции».

### G1 — `79743f2`
- Экран «Редактировать расход» показывает фактические доли из базы (в том числе гостей; долю человека, которого уже нет в событии, — как «Бывший участник») и тип распределения («По позициям», «Точные суммы», «Долями», «Поровну»).
- Если сумма и состав не менялись, доли и пересчёт в валюту события уходят **без изменений**: свежий курс не подставляется, иначе валютный расход «сам» менялся бы при каждом сохранении.
- Если сумма изменилась, а доли неравные, они пересчитываются пропорционально **в копейках**. Сумма долей строго равна итогу. Лишние копейки получают участники с наибольшим остатком, при равенстве — по id участника, одинаково на всех устройствах. Старые доли показываются зачёркнутыми рядом с новыми, сверху — предупреждение.
- «Поровну» включается **только кнопкой** «Поделить поровну»; есть обратная кнопка «Вернуть прежние доли». Пока доли неравные, состав участников не меняется случайным нажатием.
- Сетевой режим: новая колонка `expenses.split_mode` (`equal|exact|items|shares`, пусто = неизвестно), параметр `p_split_mode DEFAULT NULL` в `add/update_expense_with_splits`. Старые функции с 9 аргументами заменены одной функцией с 10, без перегрузки: при двух версиях PostgREST не смог бы выбрать функцию (PGRST203). Старые клиенты продолжают работать.
- Тесты: `test/split-rescale.test.mjs` (в т.ч. 2000 случайных случаев и суммы до 999 999 999,99), `test/expense-split-mode-rls.test.mjs`, `e2e/edit-expense-splits.spec.ts`: создать «по позициям» → открыть → сохранить без изменений → доли те же; сумма 30,80 → 61,60 → доли 30,80 / 26,40 / 4,40.

## Риски

- **Порядок выкладки.** Веб-сборка раньше миграции `20261011000000` сломает список расходов у всех. Старые мобильные сборки не пострадают.
- **Realtime удаления гостя на других устройствах** не проверен живьём. Supabase может не пропускать DELETE-события через фильтр по `group_id`; тогда удалённый гость исчезнет у других участников только при возврате на экран.
- **Права на переводы гостя — решение оркестратора, а не владельца.** Любой участник может отметить «аккаунт A → гость» за A, и сам A не может удалить такую запись (может только автор). В закрытом событии перевод между аккаунтами по-прежнему записывается, а перевод с гостем — нет. Нужно продуктовое решение владельца.
- **Нагрузка на главной.** Расходы всех событий грузятся параллельно. Для бета-масштаба это нормально; для тяжёлых аккаунтов нужна серверная сводка (`todo.md` P1-15).
- **Правка старого расхода с вышедшим участником** по-прежнему отклоняется базой («вне группы»). Экран теперь хотя бы показывает такую долю, а не теряет её.
- **На публичных страницах нет правовой формы** («ООО»/«ИП») — так требует правило владельца. Для проверки стором и для российского закона о персональных данных этого может не хватить: решить владельцу.
- **WebKit / iPhone не проверялись**: на этой машине нет системных библиотек, WebKit прогоняет CI.
