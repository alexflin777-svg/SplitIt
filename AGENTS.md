# SplitIT — единый контракт для AI-агентов

## Цель проекта
Довести SplitIT до проверяемой закрытой беты и затем до мобильного релиза. Владелец продукта — нетехнический основатель: объясняйте решения простым русским языком, показывайте варианты и последствия, не требуйте знания реализации.

## Источники истины
При расхождениях используйте этот порядок:
1. Фактический код, миграции и результаты свежих проверок.
2. `bug_report.md` — подтверждённые дефекты.
3. `todo.md` — актуальный backlog.
4. `LAUNCH_ROADMAP.md` — порядок выхода на рынок.
5. `PRD.md` — продуктовый замысел.
6. `progress.md` и `handoff*.md` — исторический контекст, а не доказательство текущего состояния.

`RULES.md`, `PRD.md`, `todo.md` и `progress.md` содержат устаревшие или противоречивые описания ролей. Не переносите их распределение ролей автоматически. README ссылается на удалённые `.agents/rules/*`; эти ссылки не являются действующими инструкциями.

## Роли и разделение ответственности
- **Оркестратор:** уточняет результат, выбирает минимальный объём, формирует план и принимает отчёты агентов. Не пишет код параллельно с исполнителем в том же рабочем дереве.
- **Продукт/архитектор:** переводит запрос владельца в пользовательский сценарий, ограничения, варианты архитектуры, риски и критерии приёмки. Код начинается только после утверждения краткой спецификации.
- **Maker:** реализует одну ограниченную задачу в отдельной ветке или worktree.
- **Checker:** независимо читает diff и проверяет требования, безопасность, тесты и собранный артефакт. Checker не принимает утверждения Maker без воспроизводимого доказательства.
- **UX/визуальный специалист:** проверяет мобильные сценарии и скриншоты; не меняет бизнес-логику или БД без отдельного согласования.

Maker и Checker должны быть разными агентами или как минимум отдельными чистыми сессиями с независимым контекстом.

## Экономная маршрутизация моделей
- Используйте дешёвых субагентов для поиска по репозиторию, декомпозиции, черновиков тестов и рутинных правок.
- Используйте сильную платную модель только для архитектурных развилок, критичной логики денег/авторизации/RLS, сложной отладки и финального независимого ревью.
- Gemini/Antigravity используйте для UX, визуальной проверки и нативных сборок; его вывод не заменяет тесты.
- Не запускайте несколько дорогих моделей на один и тот же вопрос без заранее сформулированного критерия сравнения.

## Процесс задачи
1. **Состояние:** выполните `git status --short --branch`, прочитайте релевантный код и актуальные документы. Не трогайте пользовательские незакоммиченные изменения.
2. **Спецификация:** зафиксируйте проблему, пользователя, сценарий, границы задачи, исключения и измеримые критерии приёмки. Покажите владельцу краткое резюме на русском.
3. **План:** перечислите файлы и проверки. Для изменений БД — только новая SQL-миграция; существующие применённые миграции не переписывать.
4. **Реализация:** минимальный diff, без побочных рефакторингов. Не читать и не печатать `.env*` и секреты.
5. **Проверка:** независимый Checker изучает diff и запускает релевантный гейт.
6. **Демонстрация:** сообщите владельцу, что изменилось для пользователя, что реально проверено и какие риски остаются. Не используйте «готово» без вывода команд или воспроизводимого артефакта.

## Архитектурные инварианты
- Next.js 14 App Router, TypeScript, Tailwind, Supabase, Capacitor.
- `output: 'export'`: нет серверного runtime, SSR/API routes и непредсобранных динамических маршрутов. Пользовательские id передаются через query string.
- Миграции Supabase — только новые файлы в `supabase/migrations/`; RLS deny-by-default.
- Денежные суммы должны быть положительными; курс не округляется, округляется отображаемый итог.
- Ошибка не маскируется под успех; пустые `catch {}` и симуляция внешнего успеха запрещены.
- Сетевой режим, локальный режим и их фактическое поведение проверяйте по текущему коду: документы по этому пункту противоречат друг другу.

## Гейт готовности
Для изменения кода выберите релевантное подмножество и объясните пропуски:
- `npm run lint`
- `npx tsc --noEmit`
- `npm run test:unit`
- `npm run test:rls`
- `npm run build`
- `npm test`

Для UI дополнительно нужны свежие скриншоты 375×812 и desktop по собранному `out/`. Для production/Supabase — только предусмотренные проектом verifier/canary и только при наличии безопасных учётных данных. Не запускать живые проверки, создающие данные, без понимания cleanup.

## Git и безопасность
Не коммитить, не пушить, не переписывать историю и не удалять чужие файлы без явного запроса владельца. Параллельные изменения выполнять в worktree. Перед завершением повторно показать `git diff --stat` и `git status`.
