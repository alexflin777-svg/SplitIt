# Совместная работа нескольких агентов

Дополняет `antigravity2_core.md`. Тот документ отвечает на вопрос «кто за что
отвечает», этот — «как не подраться за файлы, работая с разных машин».

**Единственный источник правды — GitHub**, `git@github.com:alexflin777-svg/SplitIt.git`.
Работа, которая существует только на чьей-то машине, не существует.

---

## 1. Параллельно или последовательно

Оба, но на разных уровнях. Это не компромисс, а следствие того, как устроен
конвейер.

**Внутри одной задачи — последовательно.** Роли ① → ② → ③ → ④ не независимы:
CODEX встраивает то, что написал Claude Code, Чекер проверяет то, что встроил
CODEX, Gemini чинит то, что нашёл Чекер. Запускать их одновременно на одной
задаче бессмысленно: второй будет работать по коду, которого ещё нет.

**Между задачами — параллельно.** Две разные задачи живут в двух ветках и не
знают друг о друге. Здесь машин может быть сколько угодно.

```
main ─────●──────────────●───────────────●────────►
           \            /  \            /
            ●──●──●────●    ●──●───────●
            задача A         задача B
        ①→②→③→④ по очереди   параллельно A
```

Практический предел — две-три задачи одновременно. Дальше растёт не скорость,
а время на разбор конфликтов.

---

## 2. Ветка на задачу, не на роль

Ветка `codex/...` или `gemini/...` — ошибка: роли передают работу друг другу
внутри одной задачи, и ветка на роль превращает передачу в merge.

```
feat/multiuser-invites      задача, все четыре роли работают по очереди
fix/rls-permissive          задача
chore/git-hygiene           задача
```

Имя — по сути задачи, не по исполнителю.

---

## 3. Цикл для любой машины и любой оболочки

Одинаков для Claude Code, CODEX, Gemini и человека.

```bash
# 1. Взять задачу
git fetch origin
git switch -c feat/<задача> origin/main

# 2. Работать. Коммитить часто, мелко, с осмысленными сообщениями.
git add <файлы>            # никогда git add -A вслепую
git commit -m "..."

# 3. Отдать работу — сразу, а не в конце дня
git push -u origin feat/<задача>

# 4. Перед передачей следующей роли: подтянуть main и убедиться, что не сломалось
git fetch origin
git rebase origin/main     # линейная история; при конфликте см. §5
npm run lint && npx tsc --noEmit && npm run test:rls && npm test
git push --force-with-lease

# 5. Влить, когда задача прошла все четыре роли
gh pr create --fill --base main
gh pr merge --squash --delete-branch
```

**`--force-with-lease`, не `--force`.** Первый откажется затирать чужой push,
второй затрёт молча.

---

## 4. Что снимает большую часть конфликтов заранее

Зоны из `antigravity2_core.md` §1 — это не только про ответственность, но и про
файлы. Если их соблюдать, два агента почти никогда не редактируют одну строку.

| Роль | Файлы |
|---|---|
| ① Claude Code | `src/lib/**`, `supabase/migrations/**`, `test/**`, конфигурация сборки |
| ② CODEX | те же файлы, но только приведение к проекту; плюс `e2e/**` |
| ③ Чекер | `bug_report.md`, `bug_reports/**` — и больше ничего |
| ④ Gemini | `src/app/**` в части разметки и стилей, `globals.css`, `tailwind.config.ts` |

Четыре файла конфликтуют чаще всего, потому что их правят все:

- `handoff.md` — **пишет только сдающая роль**, остальные читают;
- `progress.md` — дописывается сверху, новая запись не трогает старые;
- `bug_report.md` — переписывает только Чекер, прошлый круг уезжает в `bug_reports/`;
- `package.json` — правки в `scripts` согласуются заранее.

---

## 5. Конфликты

**Правило разрешения:** побеждает не та сторона, что новее, а та, у которой
есть доказательство. Тест, вывод команды, скриншот. Если доказательств нет ни
у кого — работа возвращается в ① Claude Code, а не склеивается наугад.

**Миграции не мержатся.** Две ветки, добавившие миграцию с одинаковой датой,
дают неопределённый порядок применения. Имя миграции содержит время создания
до секунд; при коллизии более поздняя переименовывается, а не правится.
Применённую к базе миграцию нельзя менять никогда — только новой миграцией
поверх.

**Сгенерированное не разрешается вручную.** Конфликт в `package-lock.json`
чинится через `npm install`, а не редактированием.

---

## 6. Чего не делать

- **`git push --force` в `main`.** Историю `main` переписывали один раз, чтобы
  убрать 590 МБ артефактов, и это было до появления соавторов. Больше — нет.
- **`git reset --hard` при незакоммиченной работе.** Откатывает правки в
  отслеживаемых файлах без предупреждения; вернуть можно только из reflog, если
  коммит успел появиться. Для отмены коммита есть `--soft`, он двигает только
  HEAD.
- **`git add -A` без просмотра.** Так в репозиторий уехали `node_modules`,
  сборки, три мобильных бинарника и `.env.local`. Смотреть `git status` перед
  каждым `add`.
- **Работать в `main` напрямую.** Даже для однострочной правки: ветка стоит
  десять секунд, разбор конфликта в `main` — полчаса.
- **Держать работу локально.** Незапушенная ветка невидима для остальных, и
  вторая роль начнёт делать то же самое.

---

## 7. Передача между ролями

Работа считается переданной, когда выполнено всё:

1. Ветка запушена, дерево чистое.
2. Гейт зелёный: `npm run lint`, `npx tsc --noEmit`, `npm run test:rls`, `npm test`.
3. `handoff.md` заполнен, включая раздел «осознанно не сделано».
4. В сообщении следующей роли — имя ветки и что именно проверить.

Пункт 3 обязателен: без него следующая роль начинает с восстановления
контекста по диффу, а это медленнее, чем написать пять строк.
