# Antigravity 2 — Правила агентов проекта SplitIT

Версия 2.1. Заменяет первую редакцию из 4 принципов. Причина замены: первая редакция
описывала намерения, но не содержала ни одного проверяемого условия, поэтому все
четыре принципа нарушались молча. Аудит от 2026-07-31 (`bug_report.md`) нашёл
2 блокера, 2 критичных и 5 серьёзных дефектов при том, что `tsc --noEmit` проходит
чисто, а `progress.md` отмечает все задачи выполненными.

Каждое правило ниже сформулировано так, чтобы его можно было проверить командой
или увидеть в артефакте. Правило, которое нельзя проверить, — это не правило.

## 1. Конвейер и роли

Работа идёт по кругу из четырёх ролей. У каждой роли свой вход, свой выход и
своя зона ответственности. Роль не берётся за чужую зону.

```
        ┌──────────────────────────────────────────────────────────┐
        │                                                          │
        ▼                                                          │
 ① Claude Code ──▶ ② CODEX ──▶ ③ CODEX/Чекер ──▶ bug_report.md ──▶ ④ Gemini/Antigravity
     логика           review +       build + Playwright              UI/UX, визуал
                      встраивание
     бэкенда/API      в проект      + живой прогон                  │
                                                                    │
        └────────────── новые дефекты возвращаются в ① ─────────────┘
```

### ① Claude Code — логика бэкенда и API

**Зона:** `src/lib/**`, серверная логика, схема данных, `supabase/migrations/**`,
контракты API, маршрутизация, конфигурация сборки и окружения.

**Не трогает:** цвета, отступы, анимации, тексты интерфейса, компоновку экранов.
Увидел визуальный дефект — записал в `bug_report.md` с пометкой «зона Gemini»,
но не правит.

**Выход:** изменённый код + запись в `handoff.md` (см. §3) + перечисление того,
что должен проверить Чекер.

### ② CODEX — встраивание в проект

**Зона:** приведение изменений от ① к тому, как реально устроен этот проект:
импорты, соседние вызовы, миграция вызывающего кода, удаление старых путей,
согласование типов и имён с существующими.

**Правило встраивания:** после CODEX в репозитории не должно остаться двух
способов сделать одно и то же. Если ① добавил новый путь входа — старый удаляется
в том же заходе, а не «потом».

**Выход:** ветка, которая собирается, плюс список файлов, которые он затронул
сверх того, что пришло от ①.

### ③ Чекер — сборка и тесты

**Зона:** запуск проверок, сбор фактов, ведение `bug_report.md`. Ничего не чинит.

Чекер — это отдельная фаза CODEX, а не ещё один агент с неясной ответственностью.
Между фазами ② и ③ CODEX прекращает менять продуктовый код: сначала завершает
ревью и встраивание, затем в роли Чекера проверяет уже зафиксированный срез.

Обязательный набор (все шесть, в этом порядке, ни один не пропускается):

```bash
npm run lint          # обязан завершаться без интерактивного мастера
npx tsc --noEmit
npm run test:rls      # политики RLS на настоящем PostgreSQL
npm run build         # production-сборка с текущим .env.local
npm test              # детерминированная local-сборка + Playwright
npm run serve:out     # запустить, пройти smoke вручную и корректно остановить
```

Production- и E2E-сборка — два разных проверяемых артефакта. `npm run build`
проверяет настоящий `.env.local`; `npm test` через `pretest` пересобирает `out/`
с пустыми внешними ключами, чтобы локальные E2E не зависели от окружения
разработчика. Прямой `npx playwright test` запрещён: он минует `pretest` и может
проверить устаревший или production-артефакт. Сборка не выполняется внутри
`webServer.command`, чтобы её ошибка не маскировалась таймаутом порта.
Подключение к уже поднятому серверу запрещено всегда
(`reuseExistingServer: false`): иначе тесты проходят на чужом или устаревшем
артефакте. Порт задаётся переменной `PLAYWRIGHT_PORT` (по умолчанию 4173), так
что параллельные прогоны разводятся без гонки. Playwright ждёт `/__ping`, а не
корень — этот адрес отдаёт `BUILD_ID` проверяемой сборки, поэтому посторонний
статический сервер границу не пройдёт.

**Правило про `tsc`.** Зелёный `tsc` ничего не доказывает. В аудите 2026-07-31
`tsc` был зелёным при двух блокерах. Чекер не имеет права писать «проверено»,
опираясь только на типы.

**Правило про сборку.** Проверять нужно `out/`, а не `next dev`. Дефект S0-2
(созданное событие отдаёт 404) не воспроизводится в dev-режиме вообще —
он существует только в статическом экспорте, то есть ровно в том, что уезжает
в APK и IPA.

**Выход:** `bug_report.md` (формат в §5). Если дефектов нет — явная строка
«дефектов не найдено» с перечислением того, что именно прогонялось.

### ④ Gemini в Antigravity — UI/UX и визуальные дефекты

**Зона:** `src/app/**/*.tsx` в части разметки и стилей, `globals.css`,
`tailwind.config.ts`, анимации, адаптив, тексты интерфейса, состояния
загрузки/пустоты/ошибки.

**Не трогает:** `src/lib/**`, схему данных, авторизацию, маршрутизацию.
Нужна правка в логике — заводит пункт в `bug_report.md` для ①.

**Выход:** правки + скриншоты «до/после» на 375×812 и 1280×720.

## 2. Общие принципы (сохранены из версии 1, уточнены до проверяемых)

1. **Diverge–Converge.** Перед задачей дороже одного файла — три варианта решения
   с одним абзацем «что ломается» на каждый, потом выбор с обоснованием.
   Для однострочных правок не требуется.
2. **Качество интерфейса.** Переходы 300 мс, микровзаимодействия, ничего не
   прыгает при загрузке. Проверяется скриншотами «до/после» на двух ширинах.
3. **Самопроверка.** Изменение считается проверенным, только если приложено
   доказательство: вывод команды, скриншот или тест. «Я проверил» без артефакта —
   не проверка.
4. **Качество кода.** Модульный TypeScript с явными типами. `any` допустим только
   с комментарием, объясняющим, почему тип неизвестен.

## 3. Контракт передачи между ролями

Передача роли — это запись в `handoff.md` в корне проекта. Без неё следующая роль
не начинает работу. Формат:

```markdown
## <дата> — ① Claude Code → ② CODEX

**Что сделано:** одна фраза.
**Изменённые файлы:** список с путями.
**Новые инварианты:** что теперь обязано быть истинным (см. §4).
**Что должен проверить Чекер:** конкретные сценарии, не «всё работает».
**Осознанно не сделано:** что осталось и почему.
```

Раздел «осознанно не сделано» обязателен. Пустой раздел пишется как «нет» —
он не удаляется. Молчаливое сужение задачи — самый частый способ потерять дефект
между ролями.

## 4. Инварианты проекта

Это утверждения, которые обязаны быть истинными после любого изменения. Каждый
выведен из реального дефекта, найденного в этом репозитории. Чекер проверяет их
поимённо.

### И-1. Пароль проверяет только Supabase

При настроенном Supabase `signInUser` не создаёт локальную сессию до успешного
`signInWithPassword`. Ошибка авторизации возвращается наверх как `error`, а не
проглатывается. В явно помеченном offline-режиме допустима локальная credential-
проверка, но она не выдаётся за серверную идентичность. Профиль без проверки
пароля допустим ровно в одном месте — в явной кнопке демо-входа.

*Проверка:* вход с заведомо неверным паролем не создаёт
`localStorage['splitit_local_user_session']`.
*История:* дефект S0-1, вход по любому паролю на любой email.

### И-2. Любой созданный пользователем id открывается в статической сборке

Маршруты не полагаются на `generateStaticParams` для сущностей, id которых
создаётся в рантайме. Пока действует `output: 'export'`, детали события живут
на клиентском маршруте.

*Проверка:* в `out/` создать событие, перейти по нему, получить экран события,
а не `404.html`.
*История:* дефект S0-2, `group-${Date.now()}` против трёх зашитых id.

### И-3. Пустая или плейсхолдерная конфигурация падает громко

Приложение при старте проверяет `NEXT_PUBLIC_SUPABASE_URL` и
`NEXT_PUBLIC_SUPABASE_ANON_KEY`. Значение, содержащее `placeholder`, — это
видимая ошибка в интерфейсе и в консоли, а не тихий переход на локальный режим.
Дефолты вида `'https://placeholder-splitit.supabase.co'` в `createClient`
запрещены: они превращают отсутствие бэкенда в невидимое состояние.

*Проверка:* `grep -r placeholder out/_next/static/chunks/` не находит совпадений.
*История:* дефект S1-1, плейсхолдеры уехали в выпущенные APK и IPA.

### И-4. Ошибка не маскируется под успех

Пустой `catch {}` вокруг сетевого вызова запрещён. Функция, которая может не
выполнить обещанное, возвращает честный `success: false`. Возврат `success: true`
из блока `catch` — дефект по определению.

*Проверка:* `grep -rn "catch" src/lib/` — каждый блок либо логирует и
возвращает ошибку, либо имеет комментарий, почему сбой здесь безразличен.
*История:* дефекты S1-1 и S2-2, сброс пароля всегда рапортовал об успехе.

### И-5. Realtime-канал скоупится на пользователя или группу

Никаких общих на всё приложение каналов. Входящий payload проверяется на
принадлежность перед записью. Состояние сливается, а не перетирается через
`setItem`. Подписка снимается в функции очистки — включая канал Supabase.

*Проверка:* два браузерных профиля с разными аккаунтами не видят данные друг друга.
*История:* дефекты S1-2 и S2-1, канал `splitit_live_sync` рассылал все группы и
всех друзей всем подписчикам.

### И-6. Пользовательский ввод в localStorage ограничен по размеру

Загрузка изображений проверяет `file.type` и `file.size`, изображение
даунскейлится до записи, запись обёрнута в `try/catch` с внятным сообщением.
localStorage — это ~5 МБ на всё приложение, а не файловое хранилище.

*Проверка:* загрузка фото на 8 МБ даёт понятную ошибку, а не обрыв регистрации.
*История:* дефект S2-3, `readAsDataURL` без единой проверки размера.

### И-7. У каждого блокера есть регрессионный тест

Дефект уровня S0 или S1 закрывается только вместе с Playwright-тестом, который
падал бы до починки. Без теста дефект остаётся открытым, какой бы очевидной ни
казалась правка.

*История:* `@playwright/test` числится в зависимостях с самого начала, при этом
в репозитории нет ни конфига, ни единого спека, а правило «Self-Verification
using Playwright» из версии 1 было невыполнимо физически.

### И-8. Текст читается, а не просто присутствует в DOM

Карточка, объявившая градиент классами `bg-gradient-*`, обязана его получить.
В CSS-правилах для контейнеров с градиентом используется `background-color`,
а не сокращение `background`: сокращение сбрасывает `background-image` в `none`,
а Tailwind реализует градиенты именно через него.

*Проверка:* `e2e/contrast.spec.ts` — вычисленный контраст текста к фактическому
фону не ниже 1.5 на всех основных экранах.
*История:* `.stitch-card { background: #ffffff }` гасил градиент на шести
экранах, белый текст оказывался на белом фоне. Пропадала в том числе сумма
расходов события — главный показатель приложения. Ни типы, ни проверки текста
такого не видят: текст в DOM есть, он просто не читается.

### И-9. RLS закрывает данные по умолчанию

Для пользовательских таблиц запрещены политики `FOR ALL USING (true)` и
публичный `SELECT USING (true)`. У каждой операции есть `USING` и, для записи,
`WITH CHECK`, привязанные к `auth.uid()` и членству в группе. Все таблицы с
пользовательскими или пригласительными данными включают RLS.

*Проверка:* миграция применяется в чистом тестовом проекте; два аккаунта создают
разные группы, и прямые `select/insert/update/delete` второго аккаунта на чужих
строках получают пустой результат или отказ. Проверка только текстом SQL
недостаточна.

### И-10. Приглашение передаёт реальную группу, а не только похожий id

Неизвестный `groupId` никогда не создаёт демо-группу молча. Пригласительная
ссылка содержит проверяемый токен, сервер загружает существующую группу, а
пользователь явно принимает приглашение. Ошибка или истёкший токен показываются
как ошибка и ничего не записывают локально. Одноразовый токен атомарно
расходуется при первом успешном принятии и не может добавить второго человека.

*Проверка:* браузер A создаёт группу с уникальным названием и расходом; чистый
контекст B открывает ссылку и после принятия видит то же название, участников и
сумму; контекст C получает отказ по тому же коду. Проверка только HTTP 200 не
считается.

### И-11. Денежные значения конечны и строго положительны

Расход и погашение принимаются только при `Number.isFinite(amount)` и
`amount > 0`; UI задаёт `min="0.01"`, а доменная функция повторяет проверку.
Отрицательные значения, `NaN`, бесконечность и перевод самому себе отклоняются
до записи.

*Проверка:* E2E вводит `-1000`, `0`, слишком большое значение и одинаковых
плательщика/получателя; localStorage и итоговый баланс не меняются.

### И-12. Симуляция не выдаётся за внешнее действие

Нельзя показывать успех обновления, отправки письма, синхронизации, загрузки,
платежа или деплоя, если не было подтверждённого ответа реальной системы.
Демо-функция обязана называться демо и не менять производственный статус.

*Проверка:* для каждого внешнего действия в отчёте есть наблюдаемое подтверждение
(ответ API, новый build/version hash, запись БД, письмо или deployment id), а не
только таймер и запись в localStorage.

### И-13. Политика RLS не открывает таблицу целиком

В миграциях запрещены политики вида `FOR ALL USING (true)`. Permissive-политики
в PostgreSQL объединяются через OR, поэтому одна такая политика обнуляет все
остальные ограничения на таблице. RLS включён на каждой таблице со ссылкой на
пользователя, у каждой политики записи есть `WITH CHECK`, денежные величины
ограничены `CHECK`-констрейнтами.

*Проверка:* `npm run test:rls` — миграции накатываются на настоящий PostgreSQL
(PGlite), запросы идут от лица трёх разных пользователей под ролью
`authenticated`. Статический разбор SQL в `e2e/rls.spec.ts` остаётся как
быстрый фильтр формы дефекта.

*Требование к харнессу:* он обязан падать, если роль не переключилась. Владелец
схемы обходит RLS, поэтому харнесс без такой страховки зеленеет на полностью
открытой базе — это уже случилось однажды с `SET LOCAL ROLE` вне транзакции.
*История:* дефект S0-1, пять политик `FOR ALL USING (true)` на groups,
group_members, expenses, expense_splits и settlements, плюс две таблицы вовсе
без RLS.

### И-14. Приложение не сочиняет данные вместо отсутствующих

Не найденная сущность — это состояние «не найдено», а не повод создать
похожую. Функция загрузки не пишет в хранилище.

*Проверка:* переход по ссылке на чужое событие показывает экран «недоступно»,
`localStorage` остаётся пустым.
*История:* дефект S1-1, `loadGroup` сочинял «Совместную поездку» с двумя
вымышленными участниками и сохранял её под настоящим id, из-за чего настоящая
группа уже не могла подгрузиться.

### И-15. Интерфейс не обещает того, чего система не делает

Функция, которая не реализована, не изображает работу. Прогресс-бар показывает
настоящий прогресс, сообщение об успехе появляется после настоящего успеха.

*Проверка:* `e2e/integrity.spec.ts` — экран обновлений без настроенного канала
не показывает ни версию, ни кнопку установки, ни сообщение об успехе.
*История:* дефект S1-2, «OTA-обновление» крутило таймер, писало строку версии
в localStorage и сообщало «Приложение успешно обновлено», не скачав ни байта.

### И-16. Каждая проверка — настоящий gate

Команда из обязательного набора отдаёт детерминированный код возврата и не
задаёт вопросов. Прогон тестов идёт на своём сервере и своей сборке.

*Проверка:* `npm run lint` возвращает 0 или 1 без интерактивного мастера;
`reuseExistingServer: false`, порт из `PLAYWRIGHT_PORT`, `/__ping` отдаёт
`BUILD_ID` проверяемого `out/`.
*История:* дефекты S2-3 и S2-4. `next lint` без конфига открывал мастер
настройки, а два параллельных прогона Playwright делили порт 4173 — второй
получал `EADDRINUSE` и зеленел на сервере первого.

### И-17. Сетевая идентичность берётся из Supabase Auth

При настроенном Supabase JSON в localStorage — только кэш профиля, не сессия.
`getActiveSession()` сверяет пользователя через Supabase Auth; протухший или
подменённый кэш очищается. Регистрация без выданной session (Confirm email)
показывает ожидание подтверждения и не создаёт локальный «успешный вход».
Демо- и Telegram-профили без настоящего auth-токена разрешены только в явно
локальном режиме.

*Проверка:* при `signUp` с `user != null` и `session == null` приложение не
переходит в рабочее пространство; в network-сборке кнопки демо-входа нет.

### И-18. Связанная запись атомарна

Группа и membership владельца, а также расход и его splits создаются или
обновляются в одной PostgreSQL-транзакции. Цепочка клиентских HTTP-запросов с
ручным «откатом» не считается атомарной.

*Проверка:* `npm run test:rls` намеренно передаёт некорректный split и проверяет,
что ни расход, ни частичная замена долей не остались в базе.

### И-19. DDL проходит Supabase Security Advisor

После применения миграции в живом проекте Security Advisor не содержит WARN.
Для функций в exposed-схеме недостаточно `REVOKE FROM PUBLIC`: Supabase может
выдать `anon` прямой EXECUTE через default privileges, поэтому ACL проверяется
через `has_function_privilege('anon', ..., 'EXECUTE')`.

*Проверка:* Supabase MCP `get_advisors(type: security)` возвращает пустой список,
а все клиентские RPC доступны `authenticated` и недоступны `anon`.

## 5. Формат `bug_report.md`

Один файл в корне, перезаписывается Чекером на каждом круге. Прошлый круг
уезжает в `bug_reports/<дата>.md`.

Шкала:

| Severity | Критерий |
|---|---|
| S0 | Основной сценарий не работает, либо дыра в безопасности. Релиз запрещён. |
| S1 | Заявленная функция не работает, либо утекают чужие данные. |
| S2 | Молчаливый сбой или ложное сообщение об успехе. |
| S3 | Некорректно, но сценарий проходит. |

Каждый пункт содержит: файл со строкой, шаги воспроизведения, ожидалось /
фактически, наблюдаемое доказательство (вывод, скриншот, содержимое localStorage),
направление починки и роль-исполнителя.

**Запрещено:** «возможно, связано», «вероятно, чинится сам», «не относится к нашим
изменениям» без доказательства. Утверждение «дефект был до нас» требует прогона на
базовой ветке и его вывода в отчёте. Без прогона пишется «связь не проверена».

## 6. Документация статуса

`progress.md` и `todo.md` описывают **проверенное поведение собранного
артефакта**, а не выполненные шаги.

Задача помечается `[x]` только когда соответствующий сценарий прогнан на `out/`
и результат приложен. Формулировки вида «синхронизация с Supabase PostgreSQL
настроена» недопустимы, если в сборке зашит плейсхолдер, а `catch {}` скрывает
провал — на 2026-07-31 в `progress.md` было отмечено выполненным ровно это.

Расхождение между `progress.md` и `bug_report.md` разрешается в пользу
`bug_report.md`: там есть доказательства.

## 8. Секреты

Ключи не попадают в код, в вывод команд, в отчёты и в историю оболочки.
`.env.local` не коммитится.

Конфигурация MCP может хранить API-ключ в `headers`, поэтому весь файл нельзя
печатать в лог или прикладывать к отчёту. Заголовок безопаснее аргумента процесса,
но секрет всё равно остаётся на диске: ключ ограничивается нужными Google API,
регулярно ротируется, а права файла — только для владельца.

## 9. Определение готовности

Изменение готово, когда истинно всё перечисленное:

- [ ] `npx tsc --noEmit` — без ошибок
- [ ] `npm run lint` — без ошибок и без интерактивного мастера
- [ ] `npm run build` — успешно, `out/` пересобран
- [ ] `npx playwright test` — зелёный, включая новый регрессионный тест (И-7)
- [ ] Живой прогон на `out/`, а не на `next dev`
- [ ] Затронутые инварианты §4 проверены поимённо
- [ ] Скриншоты 375×812 и 1280×720, если менялся интерфейс
- [ ] `handoff.md` заполнен, включая «осознанно не сделано»
- [ ] `progress.md` отражает проверенное поведение сборки, а не список шагов
- [ ] Нет открытых S0/S1 и нет ложных сообщений об успехе внешней интеграции

Незакрытый пункт — это незакрытая задача. Частично готово считается неготовым.
