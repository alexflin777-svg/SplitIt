# Деплой на Vercel

Код к деплою готов. Импорт репозитория и подключение домена делает владелец:
это вход в аккаунт через браузер.

Публичный адрес приложения **настраивать вручную не нужно** — он определяется
сам. Подробности в §3.

---

## Шаг 1. Импортировать репозиторий

1. [vercel.com/new](https://vercel.com/new), войти через GitHub.
2. Выбрать `alexflin777-svg/SplitIt`.
3. Framework Preset определится как **Next.js** — так и оставить.

Ничего в разделе Build & Output Settings менять не нужно. `vercel.json` в
репозитории задаёт только `framework`, всё остальное Vercel настраивает сам:
для Next.js он читает `next.config.mjs`, видит `output: 'export'` и обслуживает
статику из `out/`.

Прежняя версия `vercel.json` перечисляла `buildCommand`, `installCommand` и
`outputDirectory` вручную. Это дублировало пресет и мешало Vercel использовать
`npm ci` с локфайлом.

## Шаг 2. Прописать переменные окружения

**Settings → Environment Variables**. Минимум для production:

| Переменная | Значение |
|---|---|
| `NEXT_PUBLIC_SUPABASE_URL` | адрес проекта Supabase |
| `NEXT_PUBLIC_SUPABASE_ANON_KEY` | публикуемый ключ (`sb_publishable_…`) |

`.env.local` в репозиторий не попадает и на Vercel не читается — переменные
задаются только здесь.

**`service_role` ключ сюда вписывать нельзя.** Всё с префиксом `NEXT_PUBLIC_`
вшивается в клиентский бандл и видно любому, кто откроет исходники страницы.
Публикуемый ключ на это и рассчитан: доступ режет RLS на стороне базы.

Там же включить **Enable access to System Environment Variables** — без этого
не работает автоопределение адреса из §3.

## Шаг 3. Публичный адрес определяется сам

`NEXT_PUBLIC_APP_URL` нужен для ссылок, покидающих приложение: в Capacitor
`window.location.origin` указывает на локальный WebView и для приглашений
непригоден.

Задать его руками до первого деплоя невозможно — адрес выдаёт хостинг.
Получается «нужен URL, чтобы получить URL». Поэтому `next.config.mjs` берёт его
из системной переменной Vercel `VERCEL_PROJECT_PRODUCTION_URL`:

| Что задано | Что попадёт в сборку |
|---|---|
| ничего | `https://<проект>.vercel.app` |
| свой домен в `NEXT_PUBLIC_APP_URL` | он и попадёт, приоритет выше |
| `http://localhost:3000` | игнорируется как непригодное, сработает адрес Vercel |

`VERCEL_PROJECT_PRODUCTION_URL` содержит стабильный production-домен и
выставлена даже в preview-деплоях — ссылки-приглашения из preview ведут на
production, а не на временный адрес каждого коммита.

Свой домен подключается в **Settings → Domains**; после этого переменную можно
не трогать: Vercel сам подставит кратчайший кастомный домен.

## Шаг 4. Досогласовать Supabase

После первого деплоя известен адрес. В Supabase, **Authentication → URL
Configuration**:

- **Site URL** — адрес приложения;
- **Redirect URLs** — добавить `<адрес>/auth`, по нему возвращается сброс пароля.

Без этого письма со сбросом будут вести на localhost.

## Шаг 5. Проверить, что уехало

```bash
# адрес приложения вшит
curl -s https://<адрес>/ | grep -o '/_next/static/chunks/[^"]*\.js' | head -1

# бэкенд подключён: на экране авторизации нет баннера «Не настроен бэкенд»
```

Если баннер есть — переменные не долетели до сборки. Переменные
`NEXT_PUBLIC_*` вшиваются на этапе сборки, поэтому после их изменения нужен
**Redeploy**, а не просто сохранение.

---

## Порядок, если делать с нуля

Шаги зависят друг от друга, поэтому порядок не произвольный:

1. Применить миграции Supabase (`SUPABASE_SETUP.md`) — иначе приложение
   развернётся, увидит ключи, решит что оно сетевое и упадёт на каждом экране.
2. Импортировать репозиторий в Vercel.
3. Прописать две переменные Supabase, включить системные переменные.
4. Дождаться деплоя, узнать адрес.
5. Прописать этот адрес в Supabase Auth.
6. Пройти сценарий из семи шагов в конце `SUPABASE_SETUP.md` двумя аккаунтами.

Шаг 6 — единственная проверка, которая подтверждает PostgREST, GoTrue и
Realtime. Локальный харнесс покрывает политики базы, но не HTTP-обвязку.
