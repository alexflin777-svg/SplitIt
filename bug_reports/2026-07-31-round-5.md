## Главное за круг

**Закрыта дыра в покрытии, которая держалась три круга.** Политики RLS
проверялись разбором SQL текстом: это ловило форму дефекта, но не отвечало на
вопрос, увидит ли один пользователь финансы другого. Теперь на него отвечает
сам PostgreSQL — через PGlite, тот же движок в WebAssembly. Docker и локальный
Postgres на машине недоступны, облачного проекта нет, а проверка есть.

**Приложение стало многопользовательским по коду.** Общая база, доступ режет
RLS, приглашения по одноразовому коду, синхронизация через Postgres Changes.
Не хватает одного: настоящего проекта Supabase. Его создание требует
регистрации и входа через браузер — это шаг владельца, инструкция в
[SUPABASE_SETUP.md](SUPABASE_SETUP.md).

## Что сделано

### Схема и права

Третья миграция, [20260731000002_multiuser_support.sql](supabase/migrations/20260731000002_multiuser_support.sql):
статус события с ограничением значений, триггер `updated_at`, автосоздание
профиля при регистрации, публикация Realtime с `REPLICA IDENTITY FULL`,
индексы под фактические запросы.

В init-миграцию добавлены табличные `GRANT`. Без них роль `authenticated` не
доходит до политик и получает «permission denied»: RLS работает поверх GRANT,
нужны оба слоя, и оба должны лежать в миграции, иначе схема не воспроизводится.

### Живая проверка RLS

[test/pg-harness.mjs](test/pg-harness.mjs) поднимает PostgreSQL 18, повторяет
окружение Supabase (схема `auth`, функция `auth.uid()`, роли `anon` /
`authenticated` / `service_role`) и накатывает миграции ровно в том виде, в
каком они лежат в репозитории.

[test/rls.test.mjs](test/rls.test.mjs) — 25 проверок от лица трёх разных
пользователей: изоляция групп, расходов и профилей, невозможность вписать себя
в чужую группу, утечка кодов приглашений, подделка перевода от чужого имени,
ограничения на суммы, потеря доступа после выхода из группы.

**Харнесс проверяет сам себя.** Первая его версия использовала `SET LOCAL ROLE`
вне транзакции — конструкция там не действует, запросы молча уходили под
владельцем схемы, а владелец обходит RLS. Такой харнесс зеленел бы на
полностью открытой базе. Теперь роль и `auth.uid()` сверяются перед каждым
блоком, и несовпадение — это ошибка, а не тихий пропуск.

**Обратимость проверена:** при возврате политики `FOR ALL USING (true)` на
`groups` и `expenses` падают 10 проверок из 25.

### Слой данных

| Файл | Роль |
|---|---|
| [remote-store.ts](src/lib/remote-store.ts) | Supabase: чтение одной вложенной выборкой, запись, приглашения, подписки |
| [store.ts](src/lib/store.ts) | фасад: выбирает сетевой или локальный режим, наружу один API |

Экраны про режим не знают. `isMultiUser()` — единственное место, где он
определяется. Весь API асинхронный даже локально: иначе переход между режимами
потребовал бы переписывать каждый экран заново.

Все девять экранов переведены на фасад. Попутно убраны три подстановки
выдуманных данных: экран баланса рисовал «Участник 2», экран расчёта —
«Совместную поездку» с Максимом, форма расхода — группу из двух вымышленных
людей. Каждая из них показывала расчёт несуществующей группы как настоящий.

### Приглашения

Ссылка теперь несёт одноразовый код со сроком жизни, а не id группы. Вступление
живёт на отдельном экране [/invite](src/app/invite/InviteClient.tsx) и требует
явного нажатия.

Почему не id: политика на `group_members` разрешает прямую запись только
владельцу, а коды не видны посторонним (проверено тестом). Единственный путь в
чужую группу — функция `redeem_group_invite`, которая сверяет код и срок.

## Что нельзя закрыть без владельца

**Проект Supabase не создан.** Регистрация аккаунта и вход через браузер — не
та операция, которую выполняет агент. Пока `.env.local` пуст, приложение
работает в локальном режиме и говорит об этом прямо на четырёх экранах.

**PostgREST, GoTrue и Realtime не проверены.** Харнесс покрывает политики и
ограничения базы, то есть саму модель доступа. HTTP-обвязка Supabase
подтверждается только прогоном на живом проекте — сценарий из семи шагов в
[SUPABASE_SETUP.md](SUPABASE_SETUP.md#как-проверить-что-многопользовательский-режим-работает).

**Репозиторий.** В git по-прежнему `node_modules`, `.next`, `out` и три
APK/IPA. `.gitignore` добавлен, дальше не растёт.

## Решение по релизу

Блокирующих дефектов нет. Многопользовательский режим готов по коду и проверен
на уровне базы, но до подключения проекта Supabase приложение остаётся
однопользовательским — и честно об этом сообщает, а не изображает синхронизацию.
