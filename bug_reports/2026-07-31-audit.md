## S0-1. Полный обход авторизации: вход по любому паролю

**Файл:** [src/lib/supabase.ts:296](src/lib/supabase.ts#L296) (`signInUser`)

`signInUser` нигде не сверяет пароль. `saveLocalSession(userProfile)` вызывается **до** обращения к Supabase, ответ Supabase заворачивается в `try/catch` с пустым телом, а функция безусловно возвращает `{ data: userProfile, error: null }`. Аргумент `password` не используется ни разу.

**Воспроизведение (проверено вживую):**
1. Собрать и отдать `out/`, открыть `/auth`, вкладка «Вход».
2. Email: `totally-random-nonexistent-user@example.com` (никогда не регистрировался), пароль: `wrong-password-12345`.
3. Нажать «Войти в аккаунт».

**Ожидалось:** «Неверный email или пароль».
**Фактически:** создана сессия, редирект на `/`.

```
localStorage['splitit_local_user_session'] =
  {"id":"user-1785519966698",
   "email":"totally-random-nonexistent-user@example.com",
   "full_name":"totally-random-nonexistent-user",
   "avatar_url":"👤","preferred_currency":"RUB",...}
```

**Почему это хуже, чем выглядит.** `splitit_registered_users_registry` — общий на устройство. Если на телефоне/в браузере кто-то уже регистрировался, ввод его email с произвольным паролем отдаёт его профиль целиком (`userProfile = { ...registered }`), а вместе с профилем — доступ к его группам и расходам в этом же localStorage.

**Направление починки (бэкенд, зона Claude Code):** пароль проверяет только Supabase. Локальный профиль пишется **после** успешного `signInWithPassword`, ошибка Supabase возвращается наверх как `error`, а не глушится. Локальный fallback допустим только для явного демо-входа (`handleGuestLogin`), который уже есть отдельной кнопкой.

## S0-2. Созданное событие открывается как 404 в собранном приложении

**Файлы:** [src/app/events/new/page.tsx:64](src/app/events/new/page.tsx#L64), [src/app/events/[id]/page.tsx:3](src/app/events/[id]/page.tsx#L3), [next.config.mjs](next.config.mjs)

`handleCreate` генерирует `group-${Date.now()}` и делает `router.push('/events/' + newGroupId)`. При этом `generateStaticParams()` возвращает жёстко зашитые три id, а `next.config.mjs` включает `output: 'export'` — значит в `out/events/` физически лежат только `group-1`, `group-2`, `group-sochi-2026`.

**Воспроизведение (проверено вживую):** открыть `http://localhost:4173/events/group-1785451744682` → отдаётся `404.html` («404 | This page could not be found»).

**Радиус поражения:** APK `SplitIT-debug.apk`, оба IPA и любой статик-хостинг. Ломается главный сценарий: «создать событие → открыть его». В `next dev` баг не воспроизводится, поэтому в разработке он невидим.

**Направление починки:** для `output: 'export'` детали события должны жить на клиентском маршруте, а не в per-id странице. Варианты, по убыванию предпочтительности: (1) один статический маршрут `/events/detail` + id в query-string или в состоянии; (2) hash-роутинг; (3) отказ от `output: 'export'` в пользу серверного рантайма (тогда ломается Capacitor). Вариант «дописать id в `generateStaticParams`» не работает: id создаются в рантайме.

## S1-1. Бэкенда нет: в сборку вшиты плейсхолдеры Supabase

**Файлы:** [.env.local](.env.local), [src/lib/supabase.ts:3](src/lib/supabase.ts#L3), `out/_next/static/chunks/348-*.js`, `374-*.js`

```
NEXT_PUBLIC_SUPABASE_URL       = https://placeholder-splitit.supabase.co   (39 симв.)
NEXT_PUBLIC_SUPABASE_ANON_KEY  = placeholder-anon-key-splitit             (28 симв.)
```

Строка `placeholder-splitit` найдена прямо в собранных чанках — то есть выпущенные APK/IPA ходят в несуществующий домен. Следствия:

- Supabase Auth не работает — отсюда и живучесть S0-1: локальный fallback стал единственным путём.
- Realtime не работает — «мультиустройственная синхронизация» из `progress.md` в собранном артефакте отсутствует.
- `supabase/migrations/20260731000000_init_splitit_schema.sql` никуда не применена, схемы нет.
- `resetPasswordForEmail` не может отправить письмо ни при каких условиях.

Всё это невидимо, потому что каждый вызов Supabase обёрнут в `catch`, который ничего не логирует и ничего не возвращает наверх.

**Расхождение с документацией.** `progress.md` и `todo.md` описывают синхронизацию с Supabase PostgreSQL, сброс пароля по email и симуляцию пяти пользователей как выполненные. В собранном артефакте ни одна из этих трёх вещей не работает. Отчёты нужно перепроверить или переписать.

## S1-2. Realtime-канал общий на всех: чужие расходы затирают свои

**Файл:** [src/lib/supabase.ts:38](src/lib/supabase.ts#L38) (`splitit_live_sync`), `notifyRealtimeSync`, `subscribeToRealtimeSync`

`notifyRealtimeSync` отправляет в канал `splitit_live_sync` **весь** список групп и **весь** список друзей. Канал один на всё приложение, не на пользователя и не на группу. Приёмная сторона делает:

```ts
localStorage.setItem(LOCAL_GROUPS_KEY, JSON.stringify(payload.payload.groups));
localStorage.setItem(LOCAL_FRIENDS_KEY, JSON.stringify(payload.payload.friends));
```

без единой проверки `user_id` — при том что `user_id` в payload передаётся и мог бы фильтровать.

**Что произойдёт после починки S1-1.** Как только в `.env.local` подставят настоящий проект Supabase, любые два одновременно открытых приложения начнут обмениваться персональными данными: каждый увидит чужие группы, чужие суммы и чужой телефонный список друзей, и при этом потеряет свои. Это не гипотеза — это прямое чтение кода.

**Направление починки:** канал на пользователя (`splitit:user:<id>`) или на группу (`splitit:group:<id>`), RLS на стороне Supabase, приём с проверкой отправителя, и слияние состояния вместо `setItem` поверх.

## S2-1. Подписка Realtime не отписывается, обработчики накапливаются

**Файл:** [src/lib/supabase.ts:60](src/lib/supabase.ts#L60) (`subscribeToRealtimeSync`)

Возвращаемая функция очистки снимает только `BroadcastChannel` и `storage`. `supabaseRealtimeChannel.on('broadcast', ...)` и `.subscribe()` вызываются заново при каждой подписке и никогда не снимаются. При навигации по приложению число обработчиков растёт линейно, каждое входящее событие вызывает `callback()` N раз.

## S2-2. Сброс пароля всегда рапортует об успехе

**Файл:** [src/lib/supabase.ts:344](src/lib/supabase.ts#L344) (`resetPassword`)

```ts
catch (err: any) {
  return { success: true, message: `Запрос на сброс пароля для ${email} зарегистрирован` };

```

`catch` возвращает `success: true`. С учётом S1-1 письмо не уйдёт никогда, а пользователю каждый раз показывается подтверждение. Функция должна возвращать `success: false` и текст ошибки.

## S2-3. Аватар грузится без ограничения размера — риск QuotaExceededError

**Файлы:** [src/app/auth/page.tsx:58](src/app/auth/page.tsx#L58), [src/app/profile/page.tsx](src/app/profile/page.tsx)

`reader.readAsDataURL(file)` вызывается без единой проверки `file.size` или `file.type` (ни одного вхождения `file.size` в обоих файлах). Результат — base64-строка примерно в 1.37× от исходного файла — уходит в `localStorage` через `saveLocalSession`.

Фото с телефона на 3–8 МБ превышает квоту localStorage (~5 МБ). `localStorage.setItem` бросит `QuotaExceededError`, который в `saveLocalSession` не обработан → необработанное исключение в обработчике submit → регистрация обрывается без сообщения, возможна потеря уже сохранённой сессии.

**Направление починки:** проверка `file.type.startsWith('image/')`, лимит по размеру (~512 КБ после сжатия), даунскейл через `<canvas>` до 256×256 перед кодированием, `try/catch` вокруг записи с внятным сообщением.

## S2-4. `vercel.json` и `next.config.mjs` указывают на разные каталоги сборки

**Файлы:** [vercel.json](vercel.json), [next.config.mjs](next.config.mjs)

`output: 'export'` кладёт результат в `out/`, а `vercel.json` объявляет `"outputDirectory": ".next"`. Либо Vercel отдаёт не тот каталог, либо (при `framework: "nextjs"`) переопределение конфликтует с режимом экспорта. Каталог должен быть один — `out`.

## S2-5. Playwright установлен, но тестов нет — Чекеру нечего запускать

**Файл:** [package.json](package.json)

`@playwright/test@^1.62.1` в `devDependencies`, при этом в репозитории нет ни `playwright.config.*`, ни каталога `e2e`/`tests`, ни скрипта `test` в `scripts`. Правило `antigravity2_core.md` №3 «Self-Verification: Verify UI layout changes using Playwright/Browser MCP» физически невыполнимо, и шаг «Чекер запускает build/тесты Playwright» из пайплайна упрётся в пустоту.

Минимум, который закрывает S0-1 и S0-2 регрессиями: `playwright.config.ts` с `webServer` на `npx serve out`, плюс два спека — «вход с неверным паролем отклонён» и «созданное событие открывается, а не отдаёт 404».

## S3-1. Курсы валют захардкожены, а модуль называется live

**Файл:** [src/lib/currency.ts:13](src/lib/currency.ts#L13)

`CURRENCIES` содержит фиксированные `rateToRub` (USD 88.5, EUR 96.2, TRY 2.7 и т.д.), стартовый статус — `'fallback'`. В офлайн-сборке и при недоступном API мультивалютные расходы пересчитываются по устаревшему курсу молча. Нужен видимый маркер «курс от <дата>» в интерфейсе там, где показывается сконвертированная сумма.

## S3-2. Десктопная вёрстка `/auth` разъезжается

На 1280×720 карточка авторизации уходит за нижнюю границу, шапка с логотипом оказывается по центру страницы поверх пустого фона. На 375×812 всё корректно. Приложение де-факто mobile-only, но статический экспорт открывается и в десктопном браузере — нужен либо корректный десктопный лейаут, либо центрирование в колонке фиксированной ширины. *(Зона Gemini в Antigravity.)*

## S3-3. Кнопки-табы без `type="button"`

**Файл:** [src/app/auth/page.tsx:134](src/app/auth/page.tsx#L134), `:142`, `:150`

Три кнопки переключения режима не задают `type`, то есть получают `type="submit"` по умолчанию. Сейчас безвредно — блок лежит вне `<form>`. Станет самопроизвольным сабмитом при первом же рефакторинге, который занесёт табы внутрь формы.
